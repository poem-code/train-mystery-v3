### P0-1 绘制指令计数（F1 的最后一块）✅

- **缺口**：`engine.perf` 有 fps / renderMs / slowFrames，**没有绘制指令数**。
  规格书要求「单帧 ≤400」，现在无法量。
- **做法**：`draw.js` 每个出口（`text` / `fillRR` / `figure` / `arc` / `image`）累加 `draw.__count`，
  `engine` 每帧开头清零、帧尾写入 `perf.drawCalls` 与 `perf.worstDrawCalls`。
- **验收**：测试 262 → 266。新增 4 项：计数会累加、每帧清零、
  战斗满特效帧（Boss 二阶段 + 预告 + 粒子）实测 ≤400、诊断页能读到该数。
- **风险**：极低。只加一个整型自增，无渲染行为变化。

### P0-2 三档分辨率走查脚本化（F3）✅

- **缺口**：`preview.html` 支持任意 `w`/`h`，但只手动看过 320 / 390 两档，
  没做「6 界面 × 3 分辨率」的全矩阵。
- **做法**：新增 `tools/ui-audit.js`——无头渲染 360×640 / 390×844 / 768×1024 ×
  主城 / 路线 / 战斗 / 结算 / 图鉴 / 每日挑战，**用 `ui.getHits()` 的矩形与屏宽比对**判越界，
  不靠截图人眼（截图只能证明「我看到的那一帧没问题」）。
- **验收**：一条命令输出 PASS/FAIL 表 + 越界项清单；修完后 18 格全绿；
  脚本进 `README` 的验证表，后续每次改界面都能跑。
- **风险**：会真的查出问题（大概率在 768×1024 与 360×640 两档），要预留修复时间。

## 三、P1 · 表现与玩法补强（1—2 天，纯代码）

### P1-4 · B8 Boss 终结定格（建议第一个做）

**这是全项目投入产出比最高的一条。** Boss 战现在是两个节拍：

```
登场（B6）→ 崩开（B5 + B7）→ ??? → 胜利面板
                              ↑ 这里是空的
```

玩家把 Boss 打到 0 血，**下一帧就是结算面板**。整局唯一的高潮终点，
处理方式和打死一只普通怪完全相同——B5/B6/B7 三轮都在强化「崩开那一秒」，
而「结束那一秒」一直没人管。

- **做法**：`battle.ending` 相位（0→1，900ms）：
  敌人剪影下沉 6% + 轮廓光衰减 + 光点向上飘散 + 屏幕压暗一层，
  底部浮出一句收束文案（每个 Boss 一句，与 `hint` / `callback` 同一份数据里，叫 `epitaph`）；
  相位结束才允许点「结算」。
- **约束**：
  1. **不消耗回合、不推进层**——它只是表现。
  2. **200ms 后可点跳过**——抖音场景不能让玩家等 900ms 的动画。
  3. **普通战不做**——只给 Boss，否则每场都停一下会毁掉节奏。
- **验收**：5 个 Boss 5 句 `epitaph`；测试 +7（写入相位 / 相位中点击只跳过不结算 /
  相位结束后可结算 / 普通战不进相位 / 五句互不相同 / 文案不含规则词 / 存档不落盘该相位）。
- **风险**：中。胜利路径在 `state.js` 有多处（普攻击杀 / 反伤 / 秒杀卡 / 自爆），
  必须都走同一个收口，否则会出现「某种杀法没有定格」。**这一条是主要工作量。**

### P1-5 · 查票的反向收益

- **缺口**：「查票」只惩罚重复，玩家最优解是机械换招——**规则教出来的行为是背答案，不是做决策**。
- **做法**：连续 3 回合使用**不同**行动 → 下一击 +2 伤害，日志给一行提示。
  与查票形成对偶：重复被罚，变化有奖。
- **验收**：可测的正向收益；**必须跑九组千局**，超出 55% 红线就回退到 +1 或只在对阵查票时生效。
- **风险**：中。这是全局数值改动，会抬高通关率。**先跑基线，再改，再跑**，比对写进 `TUNING.md`。

### P1-6 · 图鉴的下一个目标

- **缺口**：图鉴有 100 条目与四档奖励，但玩家打开后不知道「差什么、下一档在哪」。
- **做法**：顶部一行「距离下一档还差 N 条（M%）」，未遇见的条目排最前，已收集的置灰后移。
- **验收**：+3 项测试（差额计算 / 排序稳定 / 满档时文案改为「已集齐」）。
- **风险**：低。
